## 2. 背景与目标

Portra 当前大厅承载两类核心交易入口：

- 需求大厅：需求方发布拍摄需求，摄影师浏览后响应。
- 橱窗大厅：摄影师发布服务橱窗，需求方浏览后发起沟通或预约。

现有系统已经支持发布需求、发布橱窗、列表展示、筛选、详情查看、响应需求、预约橱窗等主流程。但大厅列表仍停留在“固定第一页列表”阶段，无法支撑内容规模增长后的持续浏览、完整搜索和个性化匹配。

本 SRS 的目标是将大厅能力拆分为可落地的三个阶段：

1. 第一阶段完成真实分页与手动刷新，让大厅可以稳定浏览更多内容。
2. 第二阶段完成后端关键词搜索与统一排序参数，修复“只搜索当前页”的问题。
3. 第三阶段完成可解释、可回退的规则推荐排序，提高需求与橱窗的匹配效率。

自动刷新、数据库分页优化、复杂画像沉淀、曝光去重、AB 实验、机器学习或大模型推荐均不作为第一阶段强制目标。

## 3. 当前系统现状

### 3.1 前端现状

大厅主页面位于 `frontend/src/pages/hall/HallPage.jsx`。

- `demandParams()` 固定传入 `page: 1, size: 20, status: 'OPEN'`。
- `serviceParams()` 固定传入 `page: 1, size: 20, sort: 'latest'`。
- `loadDemands()` 和 `loadServices()` 只读取 `page.records`，没有保存 `page`、`size`、`total` 等分页元数据。
- 关键词 `keyword` 在前端用 `matchesKeyword()` 过滤当前返回的 records，只能搜索当前第一页。
- tab 数量展示使用当前数组长度，不是后端 total。
- 筛选变化会重新加载，但缺少统一的分页重置、加载更多、刷新状态和错误保留策略。
- 发布需求成功后跳转 `/hall?tab=demand`；发布橱窗成功后跳转 `/hall?tab=showcase`。
- 下架需求或橱窗后会重新请求列表，但没有明确处理当前页为空时的页码回退。

### 3.2 后端现状

需求大厅接口：

- `GET /demands`
- 已支持 `page`、`size`、`cityCode`、`scene`、`status`、`expectedDate`、`styleTag`、`minBudgetCent`、`maxBudgetCent`、`timeTag`
- 返回 `PageResult<DemandDto>`，包含 `records`、`page`、`size`、`total`
- 当前排序为 `updatedAt` 倒序
- 当前实现使用 `findAll()` 后在内存中过滤、排序、分页

橱窗大厅接口：

- `GET /service-packages`，兼容 `/services`
- 已支持 `page`、`size`、`cityCode/city`、`scene`、`style`、`minPriceCent`、`maxPriceCent`、`availableDate`、`timeTag`、`sort`
- 返回 `PageResult<ServicePackageCardDto>`，包含 `records`、`page`、`size`、`total`
- 当前默认排序为 `updatedAt` 倒序，另支持价格和创建时间排序
- 当前实现使用在线橱窗集合后在内存中过滤、排序、分页

### 3.3 可复用数据

需求相关字段：

- 城市、地点、场景、风格标签、时间标签、期望日期、预算区间、响应数、创建时间、更新时间、需求方昵称、需求方头像。

橱窗相关字段：

- 城市、服务区域、场景、风格标签、时间标签、可约日期、价格、作品图片、摄影师信用分、创建时间、更新时间、收藏/意向记录。

用户行为相关字段：

- 摄影师已响应需求。
- 需求方已收藏或表达意向的橱窗。
- 用户资料、摄影师 provider profile、历史发布内容。

## 4. 问题分析

### 4.1 分页问题

当前前端虽然向后端传入 `page` 和 `size`，但固定为第一页，且没有保存分页状态。因此它不是完整分页，只是第一页列表请求。

主要问题包括：

- 用户无法加载第 2 页、第 3 页内容。
- tab 上的数量不是总数，而是当前已加载数组长度。
- 刷新、筛选、下架后的页码行为不明确。
- 当前页最后一条被下架后，可能出现空白列表体验。

### 4.2 刷新问题

当前刷新分散在各业务操作中，没有统一交互。

主要问题包括：

- 没有手动刷新按钮。
- 刷新时是否保留旧列表、是否回到第一页不统一。
- 请求失败时用户可能只看到空状态，不能区分“无数据”和“刷新失败”。
- 发布成功返回大厅后缺少统一提示和详情入口。

### 4.3 关键词搜索问题

关键词目前只过滤当前页 records。若匹配内容在第 2 页或第 3 页，用户无法搜到。这是搜索语义错误，需要由后端在完整候选集合上过滤后再分页。

### 4.4 推荐排序问题

当前排序主要按更新时间或价格，不能体现用户角色、城市、风格、预算、时间、信用、响应竞争等匹配因素。

推荐排序必须在后端完整候选集合上完成，不能只对当前页 20 条 records 排序。否则第 2 页或第 3 页中更匹配的内容无法进入首页，推荐结果不成立。

## 5. 本次范围与非本次范围

### 5.1 第一阶段范围：大厅分页与手动刷新

第一阶段只完成列表可持续浏览和基础刷新闭环：

- 前端分别保存需求大厅和橱窗大厅分页状态。
- 首次加载和手动刷新使用 replace 模式。
- 点击“加载更多”使用 append 模式。
- 筛选条件变化后清空旧列表并回到第 1 页。
- tab 数量使用后端返回的 total。
- 添加刷新按钮。
- 发布成功进入对应 tab 后刷新第 1 页并显示发布成功提示。
- 下架当前页最后一条内容后处理分页边界。

### 5.2 第二阶段范围：后端关键词搜索与排序参数

第二阶段修正搜索和排序契约：

- 前端将 keyword 传给后端。
- 后端在完整候选集合中过滤 keyword，再分页返回。
- 统一需求大厅和橱窗大厅 sort 参数。
- 保持旧接口兼容：不传 sort 时仍为 latest。
- 前端不再只搜索当前页 records。

### 5.3 第三阶段范围：推荐排序与推荐理由

第三阶段增加推荐能力：

- 支持 `sort=recommend`。
- 在后端完整候选集合上进行规则打分。
- 按 `recommendScore desc, updatedAt desc, id desc` 排序后再分页。
- 返回可选 `recommendReasons`。
- 缺少画像时退化为稳定排序。

### 5.4 非本次范围

以下内容不作为前三个阶段的强制交付：

- 自动刷新作为后续增强，不纳入第一阶段必须完成项。
- 数据库分页优化作为后续性能迭代，不阻塞第一阶段。
- 中文分词、拼音搜索、同义词扩展、全文搜索引擎。
- 机器学习推荐、大模型推荐、实时特征平台。
- AB 实验、曝光去重、商业广告位、复杂运营置顶。
- 全站统一搜索引擎改造。

## 6. 用户角色与典型场景

### 6.1 需求方浏览橱窗

需求方进入橱窗大厅，希望按城市、风格、价格、时间持续浏览摄影师服务。内容较多时，需求方应能加载更多；筛选或刷新后列表状态应清晰，旧数据不应误混入新结果。

### 6.2 摄影师浏览需求

摄影师进入需求大厅，希望浏览开放需求，并优先看到更可能承接的需求。响应需求后，该需求应及时显示已响应状态，刷新或加载更多不应丢失该状态。

### 6.3 发布者发布内容后返回大厅

需求方发布需求后跳转 `/hall?tab=demand`。摄影师发布橱窗后跳转 `/hall?tab=showcase`。大厅进入对应 tab 后刷新第 1 页，显示“发布成功”的轻量提示，并提供“查看详情”入口。

不强制保证新发布内容一定出现在推荐排序首页。如果用户切换到 `latest` 排序，新发布内容应按更新时间出现在靠前位置。

### 6.4 画像不足用户浏览大厅

当用户缺少城市、风格、预算或历史行为时，推荐排序应退化为稳定排序，不能出现空列表、异常排序或不可解释结果。

## 7. 功能需求

### 7.1 第一阶段：分页状态管理

前端必须分别维护需求大厅和橱窗大厅的分页状态。每个大厅至少包含：

| 字段 | 说明 |
| --- | --- |
| page | 当前页码，从 1 开始 |
| size | 每页条数，默认 20 |
| total | 后端返回总数 |
| hasNext | 是否还有下一页，可由后端返回或前端计算 |
| loading | 首次加载或 replace 加载状态 |
| loadingMore | 加载更多状态 |
| refreshing | 手动刷新状态 |
| error | 当前请求错误信息 |

加载模式：

- 首次加载：replace 模式，请求第 1 页并替换旧列表。
- 手动刷新：replace 模式，请求第 1 页并替换旧列表。
- 筛选变化：replace 模式，清空旧列表并请求第 1 页。
- 排序变化：replace 模式，清空旧列表并请求第 1 页。
- 关键词变化并执行搜索：replace 模式，清空旧列表并请求第 1 页。
- 点击加载更多：append 模式，请求 `page + 1` 并追加 records。

tab 切换规则：

- 第一版允许 tab 切换时重置到第 1 页。
- 行为必须统一，不能一个 tab 保留页码、另一个 tab 重置页码。
- tab 数量必须使用后端返回 total，而不是当前数组 length。

分页边界处理：

- 下架或隐藏当前页最后一条内容后，应重新请求当前筛选条件下的列表。
- 如果当前页为空且 `total > 0`，应自动回退到上一页重新请求。
- 如果 `total = 0`，显示空状态。

### 7.2 第一阶段：加载更多

大厅列表应提供“加载更多”按钮或等价交互。

要求：

- `hasNext=true` 时展示加载更多入口。
- 点击后只追加下一页，不清空已加载数据。
- 加载更多失败时保留已有数据，并提供重试。
- `hasNext=false` 时展示“已展示全部符合条件内容”或隐藏加载更多入口。

### 7.3 第一阶段：手动刷新

大厅顶部应提供刷新按钮。

要求：

- 点击刷新后按当前 tab、当前筛选、当前排序、当前关键词重新请求第 1 页。
- 刷新使用 replace 模式。
- 刷新期间显示 `refreshing` 状态。
- 刷新成功后更新列表和 total。
- 刷新失败时旧列表不消失，只展示错误提示。

### 7.4 第一阶段：发布后刷新

发布需求成功：

- 跳转 `/hall?tab=demand`。
- 大厅进入需求 tab 后刷新第 1 页。
- 显示“需求已发布”的轻量提示。
- 提示中提供“查看详情”入口。

发布橱窗成功：

- 跳转 `/hall?tab=showcase`。
- 大厅进入橱窗 tab 后刷新第 1 页。
- 显示“橱窗已发布”的轻量提示。
- 提示中提供“查看详情”入口。

说明：

- 不强制保证新内容一定在推荐排序首页出现。
- 若用户切换 `latest` 排序，新内容应按更新时间靠前展示。

### 7.5 第一阶段：业务操作后刷新

需求响应后：

- 更新已响应状态。
- 可重新请求当前 tab 第 1 页或当前页，第一版建议刷新第 1 页以保持状态简单。

需求/橱窗下架后：

- 重新请求当前条件列表。
- 必须执行分页边界处理。

### 7.6 第二阶段：后端关键词搜索

前端应将 keyword 传给后端，后端在完整候选集合中过滤，而不是只过滤当前页。

需求大厅 keyword 范围：

- 标题或场景。
- 描述。
- 地点。
- 风格标签。
- 需求方昵称。

橱窗大厅 keyword 范围：

- 标题。
- 描述。
- 服务区域。
- 场景。
- 风格标签。
- 摄影师昵称。

第一版搜索能力：

- 使用 contains / like 模糊匹配即可。
- 不要求中文分词。
- 不要求拼音搜索。
- 不要求同义词扩展。
- 不要求全文搜索引擎。

### 7.7 第二阶段：排序参数

需求大厅支持：

- `sort=latest`
- `sort=recommend`

橱窗大厅支持：

- `sort=latest`
- `sort=recommend`
- `sort=price_asc`
- `sort=price_desc`
- `sort=created_asc`

兼容规则：

- 后端接口不传 sort 时保持旧行为 `latest`。
- 新大厅页面如需推荐排序，由前端显式传 `sort=recommend`。
- `sort=latest` 必须严格按 `updatedAt desc, id desc` 排序，不受推荐分影响。
- `sort=price_asc`、`sort=price_desc`、`sort=created_asc` 等确定性排序不受推荐分影响。
- `sort=recommend` 缺少画像时，退化为 `updatedAt desc, id desc`。

### 7.8 第三阶段：推荐排序

推荐排序必须由后端完成。正确处理顺序：

1. 先根据硬性筛选条件筛选候选集合。
2. 再对候选集合进行推荐打分。
3. 然后按照 `recommendScore desc, updatedAt desc, id desc` 排序。
4. 最后再分页返回 records。

禁止只对当前页 20 条 records 做推荐排序。只对当前页排序会导致第 2 页或第 3 页中更匹配的内容无法进入首页，推荐结果不成立。

## 8. 非功能需求

### 8.1 可用性

- 加载、加载更多、刷新、失败、空状态应区分清楚。
- 请求失败时应尽可能保留用户已看到的旧列表。
- 加载更多不应造成页面跳动或重复内容。

### 8.2 可解释性

- 推荐排序必须有可解释因子。
- 前端不展示具体推荐分数。
- 每张卡片最多展示 2-3 个推荐理由。
- 推荐理由必须和实际排序因子一致。

### 8.3 兼容性

- 旧接口调用方不传 sort 时仍得到 latest 排序。
- 后端暂未返回 `recommendReasons` 时，前端应正常渲染普通卡片。
- 返回结构必须保留 `records`、`page`、`size`、`total`。

### 8.4 可测试性

- 分页、刷新、关键词、排序、推荐应能通过单元测试或集成测试验证。
- 推荐打分应尽量封装为可独立测试的函数或服务方法。

## 10. 推荐算法设计

### 10.1 推荐原则

第三阶段采用克制的规则打分算法，不引入机器学习、大模型推荐、实时特征平台、AB 实验或曝光去重。

推荐只在 `sort=recommend` 时生效。其他排序模式不使用推荐分。

推荐排序必须在后端完整候选集合上完成：

1. 硬性筛选。
2. 推荐打分。
3. 全量排序。
4. 分页返回。

### 10.2 摄影师画像来源优先级

用于需求大厅向摄影师推荐需求。

优先级：

1. 摄影师 provider profile。
2. 摄影师已上线橱窗中的城市、风格、价格区间。
3. 当前筛选条件。
4. 如果仍然缺失，则使用兜底排序。

### 10.3 需求方画像来源优先级

用于橱窗大厅向需求方推荐橱窗。

优先级：

1. 当前筛选条件。
2. 最近一次发布需求。
3. 历史收藏或意向橱窗。
4. 用户资料中的城市或默认城市。
5. 如果仍然缺失，则使用兜底排序。

### 10.4 需求大厅推荐因子

推荐对象：开放需求。

目标用户：摄影师。

第一版规则：

| 因子 | 建议分值 | 说明 |
| --- | ---: | --- |
| 城市匹配 | +30 | 需求城市与摄影师画像或当前筛选城市匹配 |
| 风格匹配 | +25 | 需求风格命中摄影师画像风格 |
| 预算匹配 | +15 | 需求预算与摄影师价格区间重叠 |
| 时间匹配 | +10 到 +15 | timeTag 或 expectedDate 与近期档期匹配 |
| 响应竞争较低 | +10 | responseCount 较低时加分 |
| 新鲜度 | +10 | 更新时间越近分越高 |
| 资料完整度 | +5 | 地点、描述、预算、参考图越完整越高 |
| 当前摄影师已响应 | -100 | 已响应需求不再作为首选强推荐，或进入“已响应”状态分组 |

排序：

- `recommendScore desc`
- `updatedAt desc`
- `demandId desc`

缺少画像时：

- 退化为 `updatedAt desc, demandId desc`。

### 10.5 橱窗大厅推荐因子

推荐对象：在线橱窗。

目标用户：需求方。

第一版规则：

| 因子 | 建议分值 | 说明 |
| --- | ---: | --- |
| 城市匹配 | +30 | 橱窗城市与需求方画像或当前筛选城市匹配 |
| 风格匹配 | +25 | 橱窗风格命中需求方偏好 |
| 价格匹配 | +20 | 橱窗价格与预算区间匹配 |
| 时间匹配 | +15 | timeTag 或 availableDates 与期望时间接近 |
| 信用分 | +10 | 需要归一化，不能直接使用原始分放大影响 |
| 作品完整度 | +5 | 有封面、作品集、描述时加分 |
| 新鲜度 | +10 | 更新时间越近分越高 |
| 已收藏或有意向 | +8 | 可适度加权，但不能让已收藏内容刷屏 |

排序：

- `recommendScore desc`
- `updatedAt desc`
- `serviceId desc`

缺少画像时：

- 退化为 `updatedAt desc, serviceId desc`。

### 10.6 推荐理由

后端可以内部计算 `recommendScore`。

返回规则：

- 后端可以返回 `recommendScore` 供调试，但前端不展示具体分数。
- 前端只展示 `recommendReasons`。
- 每张卡片最多展示 2-3 个推荐理由。
- 推荐理由必须和实际排序因子一致。
- 不允许出现“风格匹配”但实际风格完全不重叠的情况。

示例：

```json
{
  "serviceId": 1001,
  "recommendReasons": ["同城匹配", "风格匹配", "近期可约"]
}
```

## 11. 前端交互需求

### 11.1 大厅顶部

第一阶段：

- 保留现有搜索框和筛选控件。
- 增加刷新按钮。
- 展示当前 tab 的后端 total。

第二阶段：

- 搜索框提交时将 keyword 传给后端。
- 增加排序选择。

第三阶段：

- 当选择推荐排序且后端返回推荐理由时，卡片展示推荐理由。

### 11.2 列表区域

- 首次加载显示加载态。
- 刷新时可以保留旧列表并显示轻量 loading。
- 加载更多只在底部显示 loading。
- 加载更多失败时保留已有卡片。
- 空状态要区分“确实无数据”和“筛选条件过窄”。

### 11.3 发布成功提示

发布后进入大厅时展示轻量提示：

- 需求：`需求已发布`
- 橱窗：`橱窗已发布`

提示中提供“查看详情”入口。

### 11.4 自动刷新后续增强

自动刷新不作为第一阶段强制需求。

后续如实现自动刷新，必须满足：

- 不打断用户正在浏览的列表。
- 不自动清空或跳回顶部。
- 只显示“有新内容，点击刷新查看”的提示。
- 用户点击提示后再刷新第 1 页。

## 12. 数据与性能要求

### 12.1 第一阶段

- 可以继续使用现有 `PageResult`。
- 前端根据 `total/page/size` 计算 `hasNext`。
- 第一阶段不强制改造后端数据库分页实现。

### 12.2 第二阶段

- keyword 应在完整候选集合上生效。
- contains / like 模糊匹配即可。
- 不要求引入全文搜索引擎。

### 12.3 第三阶段

- 推荐打分应在硬性筛选后的候选集合上执行。
- 推荐排序后再分页。
- 推荐计算应有稳定兜底排序，避免同分结果抖动。

### 12.4 后续性能优化

当数据量增长后，应将当前内存过滤分页逐步迁移到数据库条件查询和分页。该项作为后续迭代，不阻塞第一阶段交付。

## 13. 兼容性要求

1. `GET /demands` 不传 sort 时保持旧行为 latest。
2. `GET /service-packages` 不传 sort 时保持旧行为 latest。
3. 原有筛选参数必须继续兼容。
4. `records`、`page`、`size`、`total` 返回字段必须保留。
5. `totalPages`、`hasNext`、`hasPrevious` 可选。
6. `recommendReasons` 可选，前端必须兼容缺失。
7. `sort=latest`、`sort=price_asc`、`sort=price_desc` 等确定性排序不受推荐分影响。

## 14. 验收标准

### 14.1 第一阶段验收：分页与刷新

1. 给定 45 条开放需求，每页 20 条，首次显示 20 条，点击两次加载更多后显示 45 条。
2. 给定 33 条在线橱窗，每页 20 条，能够加载全部 33 条。
3. 筛选城市后，列表回到第 1 页，旧数据不残留。
4. 点击刷新按钮后，当前 tab 重新请求第 1 页。
5. 刷新失败时旧列表不消失。
6. 下架当前页最后一条内容后，不停留在空白页。
7. tab 数量显示后端 total，而不是当前已加载数量。

### 14.2 第二阶段验收：关键词与排序

1. keyword 能搜索全部数据，而不是只搜索第一页。
2. `sort=latest` 按更新时间倒序。
3. `sort=price_asc` 和 `sort=price_desc` 在橱窗大厅正常生效。
4. 不传 sort 时保持旧接口行为。
5. 筛选条件和 keyword 同时生效。

### 14.3 第三阶段验收：推荐

1. 同城、同风格、预算或价格匹配的内容在 recommend 排序下更靠前。
2. 已响应过的需求不会继续作为首选强推荐给同一个摄影师。
3. 缺少画像的用户仍能看到稳定结果。
4. 推荐理由与实际匹配因子一致。
5. `sort=latest` 不受推荐分影响。

## 15. 测试建议

### 15.1 第一阶段测试

前端测试：

- 首次加载第 1 页。
- 加载更多追加 records。
- 手动刷新 replace records。
- 筛选变化清空旧列表并回到第 1 页。
- tab total 使用后端 total。
- 下架后分页边界回退。

后端测试：

- 现有分页参数仍返回正确 `page/size/total/records`。
- `size > 50` 时被限制。
- `page < 1` 时归一到第 1 页。

### 15.2 第二阶段测试

后端测试：

- 需求 keyword 命中描述、地点、场景、风格标签、需求方昵称。
- 橱窗 keyword 命中标题、描述、服务区域、场景、风格标签、摄影师昵称。
- sort 参数兼容旧行为。
- keyword 与筛选条件同时生效。

前端测试：

- 搜索提交后请求带 keyword。
- 不再只对当前 records 做本地 keyword 过滤。
- 排序变化后回到第 1 页。

### 15.3 第三阶段测试

后端测试：

- 推荐打分因子可独立验证。
- 推荐排序先打分再分页。
- 缺少画像时兜底排序稳定。
- `sort=latest` 不调用推荐排序。

前端测试：

- 推荐理由存在时展示。
- 推荐理由缺失时卡片正常展示。
- 推荐分数不展示给用户。

## 16. 迭代计划

### 16.1 第一阶段：大厅分页与手动刷新

交付重点：

- 前端分页状态。
- 加载更多。
- 刷新按钮。
- 筛选后重置第一页。
- tab total 显示。
- 下架后分页边界处理。
- 发布成功提示和详情入口。

### 16.2 第二阶段：关键词搜索与排序参数

交付重点：

- 后端 keyword 搜索。
- 前端传递 keyword。
- sort 参数统一。
- 前端排序控件。
- 自动刷新可作为增强项评估，但不是必须。

### 16.3 第三阶段：推荐排序与推荐理由

交付重点：

- `sort=recommend`。
- 画像来源优先级。
- 规则打分。
- 推荐理由。
- 缺少画像兜底排序。

### 16.4 后续增强

可选方向：

- 自动刷新提示。
- 数据库分页查询优化。
- 标签表拆分。
- 用户画像沉淀。
- 曝光去重。
- 更细粒度的成交转化推荐因子。

## 17. 风险与待确认问题

1. 摄影师 provider profile 中可用于推荐的字段是否完整，需要确认。
2. 摄影师已上线橱窗能否稳定代表摄影师画像，需要产品和数据共同确认。
3. 需求方“最近一次发布需求”的时间窗口需要确认，例如 30 天或 90 天。
4. 已收藏橱窗加权需要限制强度，避免收藏内容长期占据首页。
5. 第一阶段 tab 切换是统一重置第一页，还是保留各自状态，需要 UI 最终确认。
6. 发布成功提示中的详情入口需要发布页把新内容 ID 传给大厅，具体传参方式待实现设计确认。
7. 后端是否在第二阶段扩展 `PageResult` 返回 `hasNext`，或由前端自行计算，需要接口实现时确认。
