# A 线 — 曹潇月（后端 & 集成层）

## A 线总结

A 线负责后端 API、订单状态机、数据库 schema、前后端集成以及个人主页核心业务模块。本轮暴露的问题集中在：订单状态机与前端工作流视图模型长期未对齐；数据库 schema 多次未及时同步造成接口 500；交付、邀请、角色切换等关键业务流程存在状态判断错误；通知文案存在英文泄漏。后续所有状态判断以后端状态机为唯一来源，禁止前端自行推断业务权限。

| D-DB-04 | `order_status_logs` 表未设置 `created_at` 字段默认值，新插入记录时间为 null | 状态变更日志时间轴无法排序显示 | 已补充 `DEFAULT CURRENT_TIMESTAMP` |
| D-DB-05 | `demands` 表 `location` 字段长度 `VARCHAR(50)` 在详细地址场景下不够 | 含区/路/楼栋的详细地址被截断 | 已扩展为 `VARCHAR(200)` |
| D-DB-06 | 旧版建表脚本使用 `CHARSET=utf8`，无法存储 emoji（需 `utf8mb4`） | 包含 emoji 的昵称/评论无法写入，报 `Incorrect string value` | 已将所有相关表和字段改为 `CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` |
| D-DB-07 | `service_packages` 与 `orders` 之间缺少 FK 约束，允许下单时引用不存在的 servicePackageId | 历史数据中存在孤立订单记录 | 已补充 FK，并清理孤立数据；旧代码在创建订单前先 SELECT 验证 serviceId |

# 共性经验总结

| # | 经验 | 涉及线 |
|---|------|--------|
| 1 | **单位转换必须做防御**：`null`/空字符串/非数字输入应有明确返回值，不依赖调用方保证合法 | A/B |
| 2 | **状态机变更通知前端**：前端工作流视图模型必须与后端状态机枚举保持同步，任何状态增减需联动更新双侧 | A/C |
| 3 | **DDL 变更必须同步测试 schema**：每次新增表或字段，需同步更新 `schema-h2.sql`，否则 CI 必然失败 | B/D |
| 4 | **部署环境差异提前调研**：Railway 封锁 SMTP、Railway WebSocket 需专项配置，应在架构评审时确认，不应等到部署才发现 | B/D |
| 5 | **占位功能不得以"可用"状态展示**：未完成的能力入口必须隐藏或禁用，避免误导用户 | C |
| 6 | **接口字段名和数据单位必须在接口文档中明确**：报价金额单位（元/分）、时间格式（LocalDateTime/ISO8601）、分页起始页（0/1）均需在文档中注明并双向确认 | A/B/D |
| 7 | **对全局 context / 全局状态的修改要在隔离环境充分验证**：Navbar fix-revert 来回说明影响面评估不足 | B/C |
| 8 | **角色/身份相关业务以后端为唯一权威**：前端不自行推断业务权限，统一以后端返回的角色和状态为准 | A/C |
